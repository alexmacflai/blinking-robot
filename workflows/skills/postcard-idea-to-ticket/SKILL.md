# Postcard idea to ticket

Use this skill when a person has a rough idea for a new Blinking Robot
postcard and wants help turning it into a GitHub issue.

## Establish context

Before asking questions, read the repository instructions, relevant durable
design guidance, the visual-language catalogue, and existing postcards that
overlap in subject, material, motion, or composition.

Do not ask about, restate, or turn into issue requirements anything already
governed by those sources. Surface an existing rule only when the person is
proposing a deliberate exception or asks about it directly.

## Interview

Start from what the person has already supplied. Ask only questions whose
answers would change the scene-specific brief or implementation judgement.
Adapt the questions to the idea; do not use a fixed questionnaire.

Useful areas to probe when unresolved are:

- the single visual idea or contradiction;
- what must be recognisable and what may stay ambiguous;
- composition, focal order, perspective, and the role of empty space;
- the spatial and material relationship between elements;
- motion: cause, consequence, rhythm, loop behaviour, and limits;
- the intended emotional temperature, humour, or unresolved reading; and
- likely legibility failures or unwanted readings.

When the scene uses a 2-bit palette accent, establish the accent-bearing
material or field, whether it is a local focus, dominant mass, or atmosphere,
and its intended distribution. Do not ask this for a monochrome-only scene.

Do not ask a question merely to make the brief feel complete. Accept a rough
answer, make a clear inference when it is safe, and flag only assumptions that
would materially change the scene.

## Confirm the scene

Before drafting the issue, summarise the understood scene in a short,
scene-specific statement. Let the person correct it when needed.

## Draft the issue

Write only the decisions that are unique to this postcard. Select headings
that fit the scene; common useful ones are **Brief**, **Visual direction**,
**Motion**, **Scene-specific acceptance criteria**, and **Gallery writing**.

Acceptance criteria must test the unique image, relationship, behaviour, or
legibility risk being requested. Do not use generic repository or design rules
as issue filler. Do not add implementation architecture unless it is a
scene-specific need.

Before creating the issue, inspect the repository's current issue metadata and
nearby relevant tickets. Identify any labels, milestone, assignee, or project
placement that are currently available and genuinely fit the work. Do not
invent metadata or hard-code repository conventions into this skill. Include
the proposed metadata with the draft.

Use the authenticated GitHub connector for GitHub work. Present the completed
draft and proposed metadata, then obtain explicit approval immediately before
creating the issue. Apply the approved relevant metadata and, after creation,
return the issue link and number.
